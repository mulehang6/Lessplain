# Understanding Frames

把源码理解组织成图，交给 Lessplain 校验、保存和呈现。本 skill 只使用插件的两个工具。

| 工具                        | 用途                                                       |
|-----------------------------|------------------------------------------------------------|
| `get_understanding_context` | 读取提问时的来源（`contextToken`、所在图）和图上的待答注释 |
| `present_understanding`     | 提交一张新图，或修订已有的图                               |

读源码、核对调用关系的方法由当前 Agent 自行决定。参数名和类型以工具自带的 schema 为准。字段细节见 [协议细则](references/protocol.md)。

## 调用方式

工具可能以两种方式出现，按当前环境实际可见的方式调用。

| 方式       | 调用                                  | 参数                                                           |
|------------|---------------------------------------|----------------------------------------------------------------|
| 直接暴露   | 调用工具名本身                        | 按 schema 填写，参数名用 schema 里的名字                       |
| 经路由调用 | 调用通用执行入口（如 `execute_tool`） | 工具名和参数写进 `command`，目标项目路径放在外层 `projectPath` |

经路由调用的示例（参数名为 camelCase）：

```
get_understanding_context
```

```
present_understanding --schemaVersion "1.4" --requestId "<新 ID>" --question "<原问题>" --graph "{\"nodes\":[...],\"edges\":[],\"evidence\":[]}" --placement root --displayTitle "<约 20 字>" --contextToken "<token>"
```

| 注意点        | 说明                                                                   |
|---------------|------------------------------------------------------------------------|
| `graph`       | JSON 字符串。放在双引号参数里时，内部双引号写成 `\"`                   |
| `projectPath` | 填用户要分析的目标项目的绝对路径                                       |
| 工具不可见    | 说明找不到哪个工具，然后停止。不伪造保存成功，也不替用户启动或重启 IDE |

## 什么时候画图

| 答案的形态                               | 处理                                             |
|------------------------------------------|--------------------------------------------------|
| 只有一个值、类型、名称或位置，没有关系   | 一句话回答，附 `文件:行`，不用标题、列表或代码块 |
| 涉及先后、条件、因果、调用或数据来源     | 画图                                             |
| 节点追问、待答注释、要求保存到插件的问题 | 画图，不论问题多短                               |

判断依据是答案的形态，不看问题字数或代码行数。`MAX_RETRY` 是多少，用一句话。`MAX_RETRY` 在哪起作用，画图。

画完后，对话里只回一行 `已呈现：<标题>`。批量处理时回 `已回答 N 条`。图表达不了、用户又必须知道的事（某项保存失败、某段源码找不到），另起一行写明。不复述图的内容。

## 工作流

### 新问题

1. 调用 `get_understanding_context`，固定提问时的来源。记下返回的 `contextToken` 和 `capabilities`。
2. 读源码，核对调用与引用关系。
3. 按下文的“好图标准”和“锚点”组织图。
4. 调用 `present_understanding`，提交新的 `requestId`、原问题、`displayTitle`、`graph`，以及第 1 步的 `contextToken`。问题是在追问当前打开的图时用 `placement=child`，无关时用 `placement=root`。
5. 核对返回的 `recordId` 与归属，然后回一行。

### 节点追问

用户粘贴插件复制的载荷（含 `contextToken`、`recordId`、`nodeId`、`nodeLabel`），并附上问题；或者说“这里”“这个节点”。

1. 载荷里有 `contextToken` 就带上它调用 `get_understanding_context`。没有就无参调用一次，取当前来源。之后界面选择变了，来源也不变。
2. 用 `placement=child` 和同一个 token 提交。`question` 填用户的原话。同一节点的多个追问由插件分组，不需要提交分组或坐标。

### 待答注释

`capabilities.pendingNoteBatch=true` 时，一次处理 `pendingBatch.items` 中的全部注释。

1. 每项用它自己的 `questionId`、原问题和 `context.token`，以 `placement=child` 提交。
2. 保存成功的注释由插件删除。失败或证据不足的注释保留，并逐项写明原因。
3. 全部处理后，用 `get_understanding_context(pendingScopeRecordId=<最初的 scopeRecordId>)` 复查本批。

细则见 [批处理](references/protocol.md#待答注释批处理)。

用户说某些注释是对图或插件的反馈，不是源码问题时，把这些 `questionId` 作为 `feedbackQuestionIds` 传给 `get_understanding_context`。插件读取成功后直接删除，不需要画图。

### 更新旧图

1. 请用户在插件中打开要更新的图，然后无参调用 `get_understanding_context`。确认返回的 `record` 就是这张图，记下 `record.revision`。
2. 逐个节点重读源码。位置还能找到，不代表解释仍然成立，条件和调用要重新核对。
3. 节点和边都不增不减时，用 `placement=revise` 提交完整的新图，`expectedRevision` 填第 1 步的 revision。
4. 需要增删节点或改动关系时，插件会拒绝修订。改用 `placement=sibling` 加第 1 步的 `contextToken` 新建一张图，它与旧图挂在同一个父级下。然后在对话里用一行说明旧图已被替代。

## 多 cluster

默认只用单 cluster，主路径放在一组。代码跨模块或节点多，都不是分组的理由。先缩小范围，或把子流程收成一个节点。

多 cluster 许可：**未允许**

确需分组时，先说明分组理由，并告知用户：多 cluster 的布局和跨组连线可能比较乱。使用当前环境可用的提问工具征询用户；没有可用的提问工具时，直接在对话中询问。用户同意后才分组，否则用单 cluster。

多 cluster 图画完后，对话里回两行：`已呈现：<标题>`，再加一句 `多 cluster 效果可以的话，以后直接分组，不再询问？`。

用户确认效果可以后，把许可状态改为 **已允许（<当前日期>）**，并把上面的询问段落替换为：

> 用户已允许多 cluster。分组能让图更清楚时直接分组，不再询问。

撤回许可的原文见 [协议细则](references/protocol.md#多-cluster-许可的撤回)。

## 好图标准

- **范围**：只回答当前问题。画主路径，细节留给用户点节点追问，不画整个子系统。
- **大小**：每张图默认不超过 8 个节点，约一屏。超过 12 个就收缩：删掉与问题无关的分支和纯转发的函数；仍然超出，把子流程收成一个节点，锚到它的入口函数。已允许多 cluster 时，每组仍按同样的上限计算。
- **粒度**：跨函数时一个函数一个节点。问题落在单个函数内部时，按逻辑块拆分，一个分支、一个循环或一段做同一件事的语句各算一个节点。除非那一行就是答案，不做单行节点。
- **label**：一行短语，约 16 字，最多两行。label 会作为 inline 提示贴在代码旁边，写这段代码做什么、得到什么，不复述代码。起点和终点用 `flowRoles` 标，不在 label 里写“开始”“结束”。
- **数据值**：用具体值说明数据怎么变化。假设的值在第一次出现的节点标“示例：”。来自测试或调试器的值标“实测：”，并写明来源。示例不能写成实测。
- **连线**：画布只显示 `control_flow` 边的 `condition`。一个节点有多条控制流出边时，每条都写 `condition`。`call` 和 `data_flow` 边没有文字，需要说明的值写进目标节点的 label。`coverage` 只在悬停时显示，用户必须看到的信息不要只放在这里。
- **推断**：只画源码或 IDE 能证实的关系。依赖注入、事件、反射、框架回调等看不到直接调用的关系，只在连通流程必需时画，标 `inferred: true`，并在 `coverage` 写依据。动机这类源码里没有的事不画节点。证据不足判断职责时，label 用文件名或类名，不编职责名。

## 锚点

每个节点都带 `anchor`，指向这个节点自己的源码。

| 字段       | 要求                                                                                                                                                 |
|------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| `path`     | 项目内的相对路径                                                                                                                                     |
| `symbol`   | 文件内的类型与成员名，用 `.` 连接，如 `LoginService.login`。可带签名，如 `LoginService.login(String)`。不含包名，不用 `#`                            |
| `text`     | 从源码原样复制的连续片段。函数节点从签名（含注解）复制到结束括号；逻辑块节点只复制自己那一块。保留缩进，换行写成 `\n`，不含 `\r`，不用省略号，不改写 |
| `version`  | 可省略，插件按 IDE 中的当前文档计算                                                                                                                  |
| `lineHint` | 片段首行的行号，只作提示，插件回填实际行号                                                                                                           |

插件保存前会校验全部锚点。有错时一次列出全部问题，这次提交不保存任何内容。修改后内容变了，换新的 `requestId` 再提交。

片段在文件中出现多次时，加长到唯一。找不到唯一片段时，如实告诉用户，不拿相近的代码凑。框架隐含的输入输出没有源码位置，不为它建节点。

## 常见错误

- 把 Git 提交号或片段的哈希当成 `version`。
- 为凑分支编造路径，或为拆图编造问题和父子记录。
- 把示例值写成实测值。
- 在 label 里写“开始”“结束”，而不用 `flowRoles`。
- 把用户必须看到的信息只放在 `coverage` 里。
- 把两个不同位置的证据匹配到同一个节点。
- 提交坐标、`decision` 或其他布局字段。
- 对话里复述图的内容。
- 保存失败时仍回复“已呈现”或“已保存”。
- 把相关性写成因果。
