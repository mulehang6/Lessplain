# Understanding Frames

Agent 读真实源码、组织理解图；插件负责保存与呈现。只使用当前 IDE 实际提供的 `get_understanding_context` 和 `present_understanding`，可经 IDEA MCP 的 router 调用，外层传入目标项目的 `projectPath`；参数以在线 schema 为准。工具不可用时不伪造保存成功，也不为连接工具自行启动或重启 IDE。字段与规则细节见 [协议细则](references/protocol.md)，产品方向见 [主设计文档](../../docs/code-understanding-design-v0.5.md)。

## 用图回答，不在对话里解释

先读源码及必要的调用、框架证据，再判断：

- **非常简单**：答案画出来只有一个节点、没有任何边，即单个值、类型、名称、位置，或无条件的是／否。在对话里用一句话回答并附 `文件:行`，不用标题、列表或代码块。
- **其余一律画图**：答案只要涉及先后、条件、因果、调用、数据来源中的任何一种，就有边，就画图。不按问题字数、代码行数或预计篇幅判断。节点追问、待答注释和用户要求保存到插件的问题，再短也画图。

例：“`MAX_RETRY` 是多少”用一句话；“`MAX_RETRY` 在哪起作用”“这里会不会抛异常”“这个值从哪来”“为什么先 save”都画图。

画图后，对话只回一行 `已呈现：<标题>`；批处理回 `已回答 N 条`。只有图表达不了而用户必须知道的事才另起一行，例如某项保存失败或某段源码找不到。不复述图的内容，不补充讲解。工具不可用时用一句话说明原因后停止，用户要求时再用文字简答。

## 工作流

### 首次理解

1. 收到问题先调用 `get_understanding_context()`，固定提问时刻的来源，并取得 `schemaVersion` 与 `capabilities`。
2. 读源码。调用和引用关系用 IDE 的引用、调用层级核实，不凭命名推断。
3. 按下文“好图标准”和“锚点”组织图。
4. 用 `present_understanding` 提交：新 `requestId`、原问题、约 20 字的 `displayTitle`、`graph`，以及第 1 步的 `contextToken`。问题在追问当前打开的图时用 `placement=child`，与它无关时用 `root`。
5. 核对返回的 `recordId`、`parentId` 符合预期，然后回一行。

### 节点追问

用户粘贴插件复制的载荷（含 `contextToken`、`recordId`、`nodeId`、`nodeLabel`，旁边是用户的问题），或者说“这里”“这个节点”。

1. 有 `contextToken` 就用它调用 `get_understanding_context`；没有时无参读取一次当前上下文。之后界面选择再变也不改绑来源。
2. 回答图用 `placement=child` 和这个 token，`question` 用用户原话。同一节点的多个追问由插件分组，不提交分组或坐标。

### 待答注释

上下文返回 `capabilities.pendingNoteBatch=true` 时，一次处理 `pendingBatch.items` 里的全部注释。每项用它自己的 `questionId`、原问题和 `context.token`，以 `placement=child` 提交。保存成功的注释由插件删除；失败或证据不足的保留，并逐项写明原因。最后用 `get_understanding_context(pendingScopeRecordId=最初的 scopeRecordId)` 复查本批。细则见 [协议细则](references/protocol.md#待答注释批处理)。

### 更新旧图

1. 让用户在插件中打开要更新的图，再无参调用 `get_understanding_context()`。确认返回的 `record` 正是那张图，`expectedRevision` 取它的 `record.revision`。
2. 逐个节点重读源码，重新取锚点，并核对解释所依赖的条件与调用。位置还能找到，不代表解释仍然成立。
3. 节点和边不增不减时，用 `placement=revise` 提交完整的新图（规则见协议细则）。需要增删节点或改动关系时插件会拒绝修订，这时用 `placement=sibling` 和第 1 步的 `contextToken` 新建一张图，它与旧图同属一个父级（旧图是根图时新图也是根图）。再在对话里用一行说明旧图已被替代。

## 好图标准

- **范围**：只回答当前问题。默认给主路径，细节留给用户点节点再追问，不要一次画尽整个子系统。
- **大小**：每张图默认不超过 8 个节点（笔记本侧边工具窗口约一屏）。超过 12 个必须收缩：先删与问题无关的分支和纯转发函数，还超就把子流程收成一个节点，锚到它的入口函数，让用户点它再追问。根图确实包含几段独立流程时可以分组，每组按同样的上限计算。不要为拆图虚构问题或父子记录。
- **粒度**：跨函数时一个函数一个节点；问题落在单个函数内部时按逻辑块拆分，一个块可以是一个分支、一个循环，或完成同一件事的一段连续语句。不做单行节点，除非那一行本身就是答案。
- **label**：一行短语，约 16 字以内，最多两行。label 也是编辑器里贴在锚点代码旁的 inline 提示，应写这段代码做什么、得到什么，不复述代码。业务起止用 `flowRoles` 表达，不在 label 里写“开始”“结束”。
- **值**：用具体值说明数据怎么变化。假设的值在首次出现的节点标一次“示例：”，后续节点不再重复；来自实际运行（测试、调试器）的值在首次出现处标一次“实测：”并写明来源。不能把示例写成实测。
- **连线**：线上只显示 `control_flow` 的 `condition`。同一节点有多条控制流出边时，每条都要写条件。`call`、`data_flow` 没有可见标签，需要说明的值写进目标节点的 label。`coverage` 只存档不显示，用户必须看到的信息不要放在这里。
- **事实与推断**：只画源码或 IDE 能证实的关系，画出来的边默认都已核实，不逐条标注。依赖注入、事件、反射、框架回调这类看不到直接调用的关系，只在连通流程所必需时才画，并在 `coverage` 写明“推断：原因”。不知道的事（如修改动机）不画节点。结构类问题证据不足时，label 用文件或类的实际名称，不编职责名；根图已分组时，把这些节点放进“未归类”组。

## 锚点

每个节点直接给 `anchor`，指向这个节点自己的源码。

- `path`：项目相对路径。
- `symbol`：文件内的类型与成员名链，用 `.` 连接，例如 `LoginService.login`；不含包名，不用 `#`。可以带参数签名，例如 `LoginService.login(String)`。
- `text`：从源码原样复制的连续片段。函数节点从签名（含注解）到结束括号；逻辑块节点只框自己的块。保留内部换行与缩进，多行用 `\n`，不含 `\r`；不用省略号，不改写代码。需要的代码不相邻时，拆成多个节点。
- `version`：用工具对完整文件计算的 SHA-256，原样复制，可带 `sha256:` 前缀；不能用 Git 提交号或片段的哈希。只读了磁盘内容时，不声称已核对 IDE 里未保存的编辑。
- `lineHint`：片段首行的行号。

片段在文件里出现多次时，加长片段直到唯一；找不到或无法唯一时如实说明，不用近似行号凑数。框架隐含的输入输出没有源码位置，不为它建无锚点的节点。提交前逐个锚点重读文件，确认片段存在且行号正确。

## 当前能力边界

项目级关系图、Project Tree 注释、真实 Trace、Diff 协议和自动任务交接都还没有接入，不把规划中的字段提交给现有工具。插件目前不能保存或回放运行事件；交接仍由用户把复制的载荷交给自己的 Agent。
