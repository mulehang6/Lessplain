# Understanding Frames

这是配套插件的工作流。先确认当前 IDE 是否实际暴露 `get_understanding_context`、`present_understanding`。工具不存在时直接说明可完成的静态分析，不伪造调用成功，不把前端合成事件称为真实 Trace。产品契约见 [主设计文档](../../docs/code-understanding-design-v0.5.md)，实际工具参数以在线 schema 为准。

写入工具使用 `schemaVersion=1` 和每次操作唯一的 `requestId`。重试同一操作时复用原 ID 与内容；内容变化时换新 ID。`present_understanding` 的图作为 JSON 字符串提交稳定节点、关系和证据，不提交坐标。节点追问携带待答注释的 `questionId`，这样即使用户已切换文件，回答仍回到原问题。

修订已有理解图时仍调用 `present_understanding`，传 `placement=revise`、`reviseRecordId` 和刚读到的 `expectedRevision`，并提交原问题及完整图；其余来源、归属和标题参数留空。修订只适用于保留节点 ID、边 ID、顺序和节点关系的图；原记录、追问和浏览位置继续沿用。版本冲突时重新读取原记录并核对源码，不能把旧请求改一个版本号后直接重试。成功重试同一请求仍复用原 `requestId` 和相同内容；任何修改都换新 ID。新问题仍用 root、child、sibling 或 explicit 新建，不借修订覆盖其他问题。

## 从问题进入

请求已带提问时的 contextToken，就沿用该来源；未带 token 且用户说“这里”“这一行”或沿已有理解追问时，先读取插件上下文。随后即使 UI 选择改变，也继续使用这次快照，不改绑到当前选择。

当前 `get_understanding_context` 返回 `context`、来源 `record`（含图及证据）、相关 `questions`，有待答注释时也返回其 `questionId`。只有 `context` 中的 token 固定提问来源；相关内容用于分析，不把后来选中的记录当作原来源。

当前快照记录来源视图及版本、源码位置和静态路径。运行回放位置及 diff 两侧片段属于后续协议范围，不能当作当前工具已经捕获的内容。用户不需要点击“冻结上下文”或选择内部归属参数。

读实际源码及必要调用证据后再生成图。只在答案是一个独立事实、不需要解释值的来源或变化、输入示例、分支或隐含框架步骤时，才在 Agent 对话用一两句话直接回答，不创建插件记录。不能按问题字数、代码行数或预计回答长度判断简单。凡保存到插件的回答都必须调用 `present_understanding` 提交有效图；节点追问即使答案简短也不能写纯文字回答。

图优先给具体的输入、动作、输出示例，节点或箭头标出值的变化；节点和关系标签用短语，不把解释段落塞进图中。示例注明是假设输入，不能称为真实 Trace。即使只问一行 `request.getParameter("username")`，也要核对实际框架行为，再用假设 HTTP 请求、请求参数、读取动作及结果之间的关系解释。节点追问用 `present_understanding` 和原 `questionId` 创建来源记录下的子图；插件会把同一父节点的追问子图放到共享画布的不同 cluster。显示标题约 20 个汉字，原始问题另行保留。先读取待答注释，再回答用户选中的问题；多条待答注释没有明确目标时先请用户选中，不能猜最新一条。节点复制操作只提供固定来源 token，不等于已提问或已发送。

来源有记录时，创建新图传 `placement=child`，默认让来源记录成为父级；确实属于同级时传 `placement=sibling`。没有来源记录时显式传 `placement=root`，或传 `placement=explicit` 及有效 `parentId`。缺少 token 时不要靠省略参数偷偷生成根问题。工具返回过期或缺失上下文时重新读取，不猜来源。

## 组织可核对的结果

每个源码锚点带项目相对文件路径、限定符号及必要签名、实际读到的文本、证据版本；行号只是提示。查不到或多个匹配时保留不确定性，不凭近似行号声明已定位。

每个步骤的锚点 `text` 应覆盖该步骤真正需要用户注意的完整、连续代码块，保留原始换行和缩进。步骤讲的是整个函数时包含函数体和结束括号；讲的是 `if`、`else`、循环或异常分支时包含整个相关分支，而不是只给声明或条件首行。一个函数中有几段不同职责时，为各步骤分别选择对应的逻辑块，避免每个节点都高亮整函数。跨越不相邻代码时拆成多个节点或证据，不把中间无关代码硬塞进锚点。`lineHint` 指向片段首行，`text` 必须与所读文件中的连续子串完全一致，不能用省略号或重写后的代码代替。

提交到插件的每个图节点都必须能定位到自身对应的源码：提供直接 `anchor`，或提供首个 `evidenceIds` 并确认它指向该节点对应的源码位置。不能把一条流程级证据复制给所有节点；只有确实对应同一段源码的节点才可共用锚点。框架隐含的输入、输出或动作若没有可核对的项目源码位置，就不要建成节点；必要时用简短的标题、连线标签或 Agent 对话说明，不能伪造锚点。当前源码定位所需的 `version` 是文件内容的 SHA-256（可带 `sha256:` 前缀），不是 Git 提交号。保存前重读源码，逐节点核对 `path`、`text`、`lineHint` 和版本；保存后读回图，确认没有无锚点节点。

跨函数的相同文本只作候选，确认迁移还需符号关系或重构证据。文本未变也不证明解释有效，要核对相关条件和依赖；无法确认时保留未知。版本覆盖未提交、未保存内容，使用稳定快照，不把“工作区”当作固定版本。

图节点表达问题相关的逻辑，边注明调用、控制流、数据流或结构关系。节点布局交给插件，不生成坐标。调用前命中不等于调用完成，安排异步保存不等于落盘。源码可定位不等于旧解释仍然有效。

控制流分支提供稳定的边标识、实际条件和分析覆盖范围，使插件能在逐步探索到分支时让用户选路。选择只是探索假设，不能据此填入运行值或已执行状态。依赖图中的多条关系不是互斥分支；异常、动态派发等未覆盖处明确保留未知。

对于项目关系图，先取 IDE 的模块、依赖、调用或引用事实，再做语义聚合。每个区域保留成员范围和证据，每条关系保留类型。无法证明的聚类用物理目录或 Unclear。Project Tree 注释用短职责，并提交对应证据版本。

解释 diff 时先固定前后版本，区分修改事实、影响与动机。删除工具的说明不等于移除工具，缺少动机证据就说明未知。流程或依赖变化可画前后关系，节点必须关联对应版本的代码；简单文本变更无需强行画图。

## 需要运行事实时

仅在任务需要且可使用原生 Debugger MCP 时采集；遵守项目的调试会话启动约定。当前接入由用户在 Agent 中提出请求，插件 UI 不假装能启动 Agent。未来集成若支持任务交接，按已实现的能力和用户授权执行。发现可用 ij-debugger 技能时采用其观测和清理流程。

为每个观察点明确“要证实什么”与“何时能读到结果”。确认计算完成、目标变量已进入作用域且可求值，再选择实际观测位置；验证行映射，不能机械地选下一行。显示锚点和观测锚点分别记录。

按 nodeId + seq 提交有序命中及当时的值快照，保留重复节点命中。区分错误、未观测、null 和真实值。携带 traceId、证据版本、lane 和完整性说明；遇到多线程、递归调用或丢失事件时，保留身份和间断，不凭相邻事件猜因果。

更新历史理解时先核对锚点和证据版本，再提交新版本并读回 `recordId`、`revision`、各节点锚点与既有追问、浏览位置。旧 Trace 保持原版本，不套用到新图。插件回放已收到的事件，不能让用户在回放中选择一条没发生的分支并称其为运行事实。
