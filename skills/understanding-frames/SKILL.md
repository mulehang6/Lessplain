# Understanding Frames

这是配套插件的工作流。先确认当前 IDE 是否实际暴露 `get_understanding_context`、`present_understanding`、`append_understanding_answer`；三个工具已在开发 IDE 中完成实际调用，但重启开发 IDE 后仍需检查 MCP 连接是否指向当前实例。工具不存在时直接说明可完成的静态分析，不伪造调用成功，不把前端合成事件称为真实 Trace。产品契约见 [主设计文档](../../prototype/docs/code-understanding-design-v0.5.md)，实际工具参数以在线 schema 为准。

本批写入工具使用 `schemaVersion=1` 和每次操作唯一的 `requestId`。重试同一操作时复用原 ID 与内容；内容变化时换新 ID。`present_understanding` 的图作为 JSON 字符串提交稳定节点、关系和证据，不提交坐标。补充回答优先携带复制载荷中的 `questionId`，这样即使用户已切换文件，回答仍回到原问题。

## 从问题进入

请求已带提问时的 contextToken，就沿用该来源；未带 token 且用户说“这里”“这一行”或沿已有理解追问时，先读取插件上下文。随后即使 UI 选择改变，也继续使用这次快照，不改绑到当前选择。

当前 `get_understanding_context` 返回 `context`、来源 `record`（含图及证据）、相关 `questions` 和按问题 ID 分组的 `answers`。只有 `context` 中的 token 固定提问来源；相关内容用于分析，不把后来选中的记录当作原来源。

当前快照记录来源视图及版本、源码位置和静态路径。运行回放位置及 diff 两侧片段属于后续协议范围，不能当作当前工具已经捕获的内容。用户不需要点击“冻结上下文”或选择内部归属参数。

读实际源码及必要调用证据后再生成图。插件内全部问答与理解结果默认保存，不按“是否值得保留”筛选；简短答疑关联原对象保存，需要新图、明显转向另一片源码或独立 Trace／Diff 上下文时创建 Frame。具体提交方式以实际工具能力为准，不把未建 Frame 当成无需保存。

回答优先给具体的输入、动作、输出示例，图节点或箭头标出值的变化；文字仅补必要约束，不复述图。示例注明是假设输入，不能称为真实 Trace。即使是简短问题，只要图比文字直观，也用 `present_understanding` 和原 `questionId` 创建来源记录下的子图；插件会把同一父节点的追问子图放到共享画布的不同 cluster。纯文字小补充用 `append_understanding_answer`；修订已有文字回答时传 `replacesAnswerId`，不要再堆叠一份可见的长回答。节点悬停的复制操作提供固定来源 token，用户的问题会和该 token 一起交接；复制本身不等于已提问或已发送。保留返回提问处的来源。

来源有记录时，创建新图传 `placement=child`，默认让来源记录成为父级；确实属于同级时传 `placement=sibling`。没有来源记录时显式传 `placement=root`，或传 `placement=explicit` 及有效 `parentId`。缺少 token 时不要靠省略参数偷偷生成根问题。工具返回过期或缺失上下文时重新读取，不猜来源。

## 组织可核对的结果

每个源码锚点带项目相对文件路径、限定符号及必要签名、实际读到的文本、证据版本；行号只是提示。查不到或多个匹配时保留不确定性，不凭近似行号声明已定位。

跨函数的相同文本只作候选，确认迁移还需符号关系或重构证据。文本未变也不证明解释有效，要核对相关条件和依赖；无法确认时保留未知。版本覆盖未提交、未保存内容，使用稳定快照，不把“工作区”当作固定版本。

图节点表达问题相关的逻辑，边注明调用、控制流、数据流或结构关系。节点布局交给插件，不生成坐标。调用前命中不等于调用完成，安排异步保存不等于落盘。源码可定位不等于旧解释仍然有效。

控制流分支提供稳定的边标识、实际条件和分析覆盖范围，使插件能在逐步探索到分支时让用户选路。选择只是探索假设，不能据此填入运行值或已执行状态。依赖图中的多条关系不是互斥分支；异常、动态派发等未覆盖处明确保留未知。

对于项目关系图，先取 IDE 的模块、依赖、调用或引用事实，再做语义聚合。每个区域保留成员范围和证据，每条关系保留类型。无法证明的聚类用物理目录或 Unclear。Project Tree 注释用短职责，并提交对应证据版本。

解释 diff 时先固定前后版本，区分修改事实、影响与动机。删除工具的说明不等于移除工具，缺少动机证据就说明未知。流程或依赖变化可画前后关系，节点必须关联对应版本的代码；简单文本变更无需强行画图。

## 需要运行事实时

仅在任务需要且可使用原生 Debugger MCP 时采集；遵守项目的调试会话启动约定。当前接入由用户在 Agent 中提出请求，插件 UI 不假装能启动 Agent。未来集成若支持任务交接，按已实现的能力和用户授权执行。发现可用 ij-debugger 技能时采用其观测和清理流程。

为每个观察点明确“要证实什么”与“何时能读到结果”。确认计算完成、目标变量已进入作用域且可求值，再选择实际观测位置；验证行映射，不能机械地选下一行。显示锚点和观测锚点分别记录。

按 nodeId + seq 提交有序命中及当时的值快照，保留重复节点命中。区分错误、未观测、null 和真实值。携带 traceId、证据版本、lane 和完整性说明；遇到多线程、递归调用或丢失事件时，保留身份和间断，不凭相邻事件猜因果。

更新历史理解时先核对锚点和证据版本，再通过实际支持的更新协议提交新版本；旧 Trace 保持原版本，不套用到新图。插件回放已收到的事件，不能让用户在回放中选择一条没发生的分支并称其为运行事实。
