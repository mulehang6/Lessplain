# Understanding Frames

Agent 负责分析真实源码并生成理解图，插件负责保存与呈现。只使用当前 IDE 实际提供的 `get_understanding_context` 和 `present_understanding`，可通过 IDEA MCP 的 router 调用；确认目标项目并传入正确的 `projectPath`。工具不可用时说明能完成的分析，不伪造保存成功，不为连接工具自行启动或重启 IDE。实际参数以在线 schema 为准；产品方向见 [主设计文档](../../docs/code-understanding-design-v0.5.md)。

## 决定如何回答

读实际源码及必要的调用、框架证据后再解释。只在答案是一个独立事实，无需解释过程、值的来源或变化、输入示例、分支或隐含步骤时，在 Agent 对话中用一两句话直接回答。不能按问题字数、代码行数或预计回答长度判断简单。用户要求保存到插件或回答节点追问时，即使答案简短，也必须提交有效图，不提交纯文字回答。

图优先表达具体输入、动作、输出及值的变化。节点与关系标签使用短语，不把长解释塞进节点；文字只补图无法表达的必要约束。示例标明是假设输入，不能称为真实执行。显示标题保持简短，约 20 个汉字，原始问题另行保留。

## 固定来源与回答追问

- 请求带有 `contextToken` 时，沿用该 token 读取来源。未带 token 且用户说“这里”“这一行”或沿已有节点追问时，先读取当前插件上下文；之后 UI 选择改变也不改绑问题来源。
- `get_understanding_context` 返回支持的 `schemaVersion`、`context`、来源 `record`、相关 `questions` 和能力标识。来源 token 在 `context.token`。确认 `capabilities.pendingNoteBatch=true` 后，默认一次处理 `pendingBatch.items` 中当前理解图及其追问的全部待答注释，不要求用户逐条选择；不扩展到其他理解图。未保存的草稿也会显示气泡，但不在待答队列内，不根据图标猜测或提交其内容。缺少该能力时说明需要加载新版，不猜测未返回的队列。
- 保存本次 `pendingBatch.scopeRecordId` 和队列快照。每项包含 `questionId`、`question` 原文、固定 `context`；来源节点在该项 `context.nodeId`，token 在该项 `context.token`，所属当前记录从 `pendingBatch.records` 按该项 `context.recordId` 匹配。不能把顶层当前节点、其他注释的 token 或当前界面选择套给整批问题。
- 逐项核对源码、解释并用有效图回答，提交各自的 `questionId`、原问题及 token。用户明确只问某一条时才缩小范围。复制载荷只是交接问题，不代表已发送给 Agent；已有 questionId 的原文和 token 仍须核对。
- 每项保存成功后，插件在同一事务中删除独立注释条目；回答图保留原问题和固定来源，不额外保留旧注释历史。失败、取消或证据不足的项不得通过删除注释冒充已回答。整批不使用一次清空操作。
- 最后用 `get_understanding_context(pendingScopeRecordId=最初的范围ID)` 复查，不能依赖回答时自动切换后的当前画布。确认本次快照中的待答 ID 已完成；仍未完成的逐项说明原因。期间新加的注释保留到下一批，不无限重复读取和自动扩展任务。
- 节点追问必须使用 `placement=child`，归属固定来源记录。同一节点的追问图由插件放在共享画布的不同分组，不生成分组坐标。
- 创建其他新图时，有来源记录默认用 `child`；确实属于同级才用 `sibling`。独立问题显式用 `root`；指定其他有效父记录时用 `explicit` 和 `parentId`。工具报告来源过期、问题已修改或已取消时重新读取核对，不猜 ID 或省略来源绕过校验。

## 组织可定位的图

每个节点必须能定位到自身对应的源码，优先提供直接 `anchor`。通过 `evidenceIds` 关联时，核对图中实际匹配的证据；当前导航在 `graph.evidence` 中取第一条匹配，而不是按 `evidenceIds` 的排列取第一条。不要让不同位置的证据匹配同一个节点，也不要把流程级证据复制给所有节点；确实对应同一段源码时才可共享锚点。

锚点使用项目相对 `path`、实际限定 `symbol`、原样 `text`、文件内容的 SHA-256 `version` 和片段首行 `lineHint`。版本可带 `sha256:` 前缀，不能使用 Git 提交号或片段哈希。以实际读取的当前源码快照为准，包括能取得的未保存内容；仅有磁盘内容时不能声称已经核对未保存文档。

`text` 覆盖步骤需要关注的完整、连续代码块，保留换行与缩进。讲整个函数时包含函数体和结束括号；讲分支或循环时包含对应逻辑块。不同职责分别选片段，不让每个节点都高亮整函数。跨越不相邻代码时拆分节点或证据，不夹带无关代码，不用省略号或改写代码代替实际子串。查不到或有多个匹配时保留不确定性，不用近似行号伪造定位。

框架隐含输入、输出或动作没有可核对的源码位置时，用简短标题、连线标签或 Agent 对话说明，不创建无源码的示例节点。图节点、关系和证据使用稳定 ID；边注明实际关系，控制流分支提供条件及分析覆盖范围。`condition` 只用于 `control_flow`；同一节点有多条控制流出边时，每条都需条件。调用和数据关系的适用条件写在 `coverage`，不伪装成控制流。多条依赖关系不是互斥分支，静态选择也不代表已经执行。节点布局交给插件，不提交坐标。

根记录默认直接展示一张图。上下文返回 `schemaVersion=4` 且 `capabilities.rootClusters=true` 时，复杂根问题可以提交单层 `clusters=[{id,title,nodeIds}]`：分组对应源码中的职责、触发入口或处理阶段，成员完整覆盖图节点且互斥；不嵌套、不提交坐标，不省略跨组真实关系。先检查原分组的线路，再考虑语义成立的合并；不能仅为少画线把无关业务混为一组。同一节点的不同追问仍由插件一问一组，子图不提交语义分组。不要为拆分流程创建无关问题或虚构父子记录。

点击节点高亮通向该节点的全部可浏览来路，已选路径与来路高亮统一流动，不因路线数量改变表现。关闭“路径流动”或启用减少动态效果时静止显示；无关连线保留普通样式。高亮表示静态图中的可浏览关系，不证明该路线已经真实执行。回路正常呈现，不为流动猜选路线或虚构业务起点。

逐步浏览与按需“补全来路”仍保留，来路选择只在用户主动操作时开始。`context.staticPath` 是当前确定的阅读路径，可能从中间节点开始，不证明完整入口、实际执行或业务条件成立；默认全部上游高亮不等于选定一条 staticPath。用户已确认的来路仅在当前画布内记忆；不要为补全路径猜入口或增加 AI 选路字段。分析节点问题仍以固定来源和实际源码为准。

业务起点和结束点由 Agent 根据当前解释范围明确标记：节点 `flowRoles` 为 `["start"]`、`["end"]` 或 `["start", "end"]`，普通节点省略或用空数组。可有多个入口和结束点；独立且一步结束的流程可同时具备两种角色。入口可以有调用或数据入边，结束点也可能继续向其他流程传递数据，所以不根据入度、出度或 `kind` 猜角色。`kind` 保留节点类别职责，不在标签手工添加起止文字或图标。

先确认上下文返回 `capabilities.nodeSemantics=true`，再提交可选的 `endOutcome`；缺少该能力时省略该字段。分支图标由插件按当前图中不同的可浏览后继数大于 1 自动显示，不提交 `decision`。可浏览关系为 `control_flow`、`call`、`data_flow`，入边不参与，同目标平行边只算一个后继；图标表示可继续探索的不同去向，不代表条件互斥或真实并发执行。分析范围只覆盖部分分支时注明覆盖范围，不为显示图标虚构路径。

结束节点可设 `endOutcome="success"` 或 `"failure"`；非结束节点不能设置结果。业务成功用 success，校验拒绝、权限不足及未恢复的异常用 failure；被捕获并恢复后继续执行的异常不能直接标成失败结束。同一节点涵盖成功和失败，或证据不足时省略结果，保持中性结束色，不为上色改写节点或拆分既有身份。正常跳过是否完成当前职责要根据解释范围核对，不能仅凭 return 或方法名分类。插件绘制蓝色起点、绿色成功结束、红色失败结束、中性未分类结束；双角色蓝底配结束结果边框。图中的分支采用与文字同字号的橙色分叉图标，卡片形状不变。

## 保存与修订

- 先核对上下文返回版本、能力标识和在线 schema。本版使用 `schemaVersion=4`；仍兼容无 `clusters` 字段的版本 3 请求。旧插件只支持版本 3 时，仅按其能力提交单图，不提交分组字段，也不绕过工具直接写数据库。`graph` 是包含 `nodes`、`edges`、`evidence` 以及可选根分组的 JSON 字符串，至少包含实际图节点。边的 `relation` 使用 `control_flow`、`call`、`data_flow`、`dependency` 或 `structure`。
- 每次操作使用唯一 `requestId`。同内容重试复用原 ID 与全部参数，内容或版本变化则换新 ID；不同内容不能占用已有 ID。
- 修订原图仍用 `present_understanding`，传 `placement=revise`、`reviseRecordId`、原问题和完整图。确认读到的 `record.id` 是修订目标，`expectedRevision` 取其当前 `record.revision`，不能使用来源快照里的旧 `context.recordRevision`。修订参数中的 `contextToken`、`questionId`、`parentId`、`displayTitle` 留空。
- 修订须保留节点 ID、边 ID、两者顺序以及每条边的起点、终点、关系类型。业务角色须对应当前源码和原分析范围，不能为染色而改写流程。记录身份、追问、标题和浏览状态沿用；新问题创建新图，不借修订覆盖。版本冲突后重新读取记录并核对源码，不能只修改版本号重试旧内容。
- 根图修订的 `clusters` 省略或为 `null` 时保留当前分组，显式 `[]` 清空，非空数组完整替换。替换的分组必须与提交节点一致；不依赖插件补成员或猜业务归属。分组更新也属于请求内容，改变保留／清空语义时换新的 `requestId`。
- 保存前重读并逐节点核对 `path`、`text`、`lineHint`、版本及证据引用。位置仍能找到不证明解释仍有效，相关条件与依赖也要核对。
- 保存后核对返回的 `recordId`、`revision`、`parentId`、`questionId` 与本次归属一致。上下文工具的 pendingScopeRecordId 用于固定并复查批量范围，不承诺能读回队列之外的新图；用户已经打开目标图时可读取其当前上下文检查，但不能据此改绑原问题。固定 token 和批量范围参数不能同时指定。

## 当前能力边界

项目级关系图、Project Tree 注释、真实 Trace、完整 Diff 协议与自动任务交接尚未接入，不把规划中的字段提交给现有工具。需要运行事实时按用户请求和项目调试规则收集真实证据，但当前插件不能保存或回放 Trace 事件；假设示例不能冒充 Debugger 观测。当前交接仍由用户把问题载荷交给自己的 Agent。
