## 项目方向上下文

本文规定产品流程和交互边界，适用于所有 UI 技术实现。[JCEF / React 设计](jcef-react-experiment.md) 说明当前实验的技术实现，旧主设计用于背景参考。

### 1. 用户本身就不喜欢读大量解释文本

这不是单纯的 UI 偏好，而是产品的核心约束。

用户长期使用 AI 辅助开发后，对大段 AI 解释已经有明显疲劳。问题不是“文字写得不够好”，而是：

- 信息量经常超过当前真正需要知道的东西。
- AI 很容易把简单问题展开成教程。
- 大量 Markdown、卡片、步骤标题会增加阅读负担。
- 看完当时可能懂了，过一两天仍然会忘。
- 相比 AI 长文，人工教程通常更好读，原因之一就是作者会主动删掉不必要的解释。

因此产品不能把“生成更好的解释文章”当核心。

真正想要的是：

> 少生成，少阅读，多看真实代码，多操作真实程序。

表达由问题决定：流程和关系用图，原因与限制用短文字，状态变化用交互。文字紧邻它解释的对象或结果，延伸细节按需展开；不为满足形式强行画图，也不把所有解释折叠掉。减少的是重复与无关信息，不是有用的说明。

---

### 2. “懒”在这里应该理解为不愿意承担额外认知成本

用户不希望为了理解项目，再维护另一套复杂工具。

典型反感对象包括：

- 配 OpenAI / Anthropic / Gemini / DeepSeek 等 Provider。
- 填 API Key、Endpoint、模型名称。
- 学另一套复杂导航。
- 大量手动确认和设置。
- 每个目录常驻一个开关、要求逐目录配置；独立控制仍保留在右键菜单。
- 为了看代码，先读一篇工具自己生成的说明。
- 为了研究一个问题，在几个 Tab、Chat 和 Tool Window 之间不断跳。

所以一个功能即使“更强”，如果要求更多操作，也可能是倒退。

产品应该默认：

> 能自动就自动，必须让用户决定时再让用户决定。

但这里的“自动”不能变成替用户猜他想研究什么。

---

### 3. 用户接手陌生项目时，本来就不知道该问什么

这推翻了早期“系统推荐值得看的场景”这个方向。

AI 可以读项目，但不能读心；“什么值得看”也没有稳定定义。

因此主流程应该是：

```text
用户在自己的 Agent 中提出当前问题
→ Agent 分析并调用 MCP 创建答案
→ 插件展示答案
→ 用户在节点或生成式组件上添加注释，或选中代码提问
→ 在插件中一键复制所有待答问题，内容保持简洁
→ 粘贴到自己的 Agent
→ Agent 分析并通过 MCP 提交对应回复
```

而不是：

```text
打开项目
→ 插件猜你应该先学 A
→ 再猜你应该看 B
→ 推荐场景 C
```

Project Tree 和 Project Graph 可以帮助用户建立全局认识，但具体问题仍然由用户驱动。

持续课程由用户主动调用 lessplain-teach。学习目标明确后，Agent 可在本次调用中结合学习记录推荐下一小节；用户随时可以指定主题。每节只教一个明确能力，用项目源码或经过核对的短样例和必要交互组织内容，提供可跳过的学习检查。代码与技术语义核验是 Agent 的备课责任，学习检查用于观察用户理解；跳过只记为看过，不阻止继续浏览。课程文件由 Agent 维护，插件仍负责页面、状态与引用。

主页直接展示全部历史记录，不放待答列表或复制按钮。工具窗口名称为 Lessplain；历史记录和在编辑器打开位于原生标题栏。输入框由具体节点、组件或源码的提问入口打开，固定当时的来源。主页不设置新问题入口，也不展示工具调用教程。复制按钮属于答案画布，包含当前理解根及所有追问的待答原文和必要引用；源码及示例状态由 Agent 通过引用读取，复制不改变问题状态。

历史行右键只显示“重命名、删除”菜单，不直接打开综合管理表单；不提供调整归属入口，追问关系由 MCP 建立。重命名只编辑名称，删除单独确认该记录及全部追问。右键操作固定目标记录，不切换当前答案。

图内控件沿用既定位置：左上放大、缩小、显示整图、一键自动排版；左下上/下一步；右侧中间复制全部问题、画布行为复合按钮，有追问层级时显示理解层级导航。复合按钮包含自动/横/纵方向、自动跳转源码、路径流动和跟随节点。步骤导航遇到多个候选时先预览、由用户确认，不自动选分支。

图页直接使用可用画布区域，不重复显示原问题或图外说明文章。每组可以在主要内容前放少量导语，在结果附近放必要解释，不设强制字数截断。节点默认只有两行以内的短句，注释、复制和追问入口在 hover 或键盘聚焦时显示。标题属于 cluster。有关联的节点放在同一图；独立职责分别成组，不能为了串成流程而连线。

整个答案页面是一个完整画布，cluster 只是其中的分组框。节点、分组、生成式组件和示例共用同一坐标系，一起平移和缩放；没有固定宽度卡片、嵌套图窗或独立图视口，外层也不出现横纵滚动条。分组导航定位画布中的分组，追问层级导航切换答案。真实关系可以跨 cluster 表达，不能为了串流程凭空加边。组件与节点通过独立状态路径双向选择。

工具窗口保留 IDEA 原生标题栏的历史与编辑器入口；在编辑器打开时只有完整画布及原有图内控件，不复制工具窗口标题栏或增加全局注释、管理按钮。节点正文、按钮栏及中间连接区保持连续 hover，按钮移回节点不隐藏；图标有明确的提示、悬停与按下反馈，空白右键只显示一份画布菜单。

节点左下角只保留注释与复制两个图标。注释弹层保留已有列表，下方只有输入框、发送图标和取消按钮，不显示节点标题、顶部关闭图标或问题/反馈切换。新注释按问题保存，旧反馈继续可读可处理。发送成功清空草稿并关闭，失败留文；取消清空新草稿并关闭，Escape/外部关闭保留。每条待答注释可直接硬删除，取消编辑只退出编辑。回答原子保存问题快照并删除待答行，回答入口留在追问树。删除或回答旧注释不清除正在输入的新草稿。源码跳转由开关和节点点击控制，不增加源码按钮。所有 tooltip 横向排字，右侧控件优先向左提示；按钮激活及程序聚焦弹层时不冒出提示遮挡内容。cluster 仅标题区域允许左键整体拖动，内部空白处穿透到画布，用右拖平移、右键打开画布菜单。

可用图标采用正常前景色，只有禁用才减亮。发送按钮默认透明、hover 蓝底；其余按钮明显灰色 hover，保留按下与键盘聚焦反馈。历史记录无序号，保留层级缩进、待答计数、新记录标识和整行灰色 hover。

注释列表统一显示序号、正文、查看详情和删除，不在网页内编辑。查看详情关闭网页弹层并保留新草稿，复用原生 Swing 问题弹层；节点和组件注释只编辑文字。从插件窗口查看编辑器选区问题时保留 IDEA Editor 预览；在源码编辑器标签内选区提问时不重复显示代码预览，保留原保存和取消操作，提供单独关闭按钮，外部点击不关闭。不要把节点锚点当成用户选区。带有明确 elementId/nodeId 归属的源码问题计入对应节点并可从节点查看；无归属源码问题仍从当前问题集合查看，不跟随当前选中节点猜归属。复制入口的左键行为仍是一键复制。

普通生成式组件的注释入口也使用图标。有待答时常驻数量标记，只有已回复历史时保留中性标记；没有注释时才按 hover/键盘焦点显示。标记按精确组件身份更新，不参与布局测量。注释与追问预览弹层位于触发图标下方 6px，空间不足时翻到上方并限制在窗口内；弹层不参与节点尺寸测量或 ELK 布局。外部点击、Escape、切换答案及画布移动关闭弹层并保留未保存草稿。

图表操作沿用旧版：左键选择／拖节点，右键拖画布，普通滚轮纵移、Shift 加纯纵向滚轮横移、Ctrl 以鼠标为锚缩放。触摸板双轴输入保留完整方向，即使宿主附带 Shift 也不丢弃纵向分量；原生可滚动区域优先消费输入。平移不添加缓动或目标队列，保留系统输入的正常惯性，不触发布局。点击节点、上／下一步和组件反向选择走同一条跟焦逻辑；默认开启，保持缩放，240ms 平滑居中，可被新选择重定向或手动操作中断。

每张画布只显示一个节点操作栏，120ms 渐显，离开连续命中区立即隐藏；键盘聚焦同样可用。再次点击当前节点仍可跟焦，不重复跳源码或修改已确认路径；重复组件状态同步继续去重。主题导出保留透明度，hover 与 pressed 在当前背景上正确合成。

窗口边界立即响应尺寸变化，节点布局和镜头保持稳定。AUTO 仅在首次布局、显式切换方向或自动排版时按当前宽度的 800px 分界选择方向；伴随组件沿用该次确定的逻辑宽度。预留空间按组件身份及折叠状态分别缓存：Tabs、Select 切回短内容不回缩，显式收起 Collapsible、Accordion 时边框随自然内容收缩。多个及嵌套折叠区不共用一个高度，缓存有上限，完整替换内容后重置。增长和收缩都保留所属分组的位置及镜头。仅实际 ELK 结构、方向或成员尺寸变化才重排，最终测量按帧合并；分组自身测量不额外触发布局。过期 Worker 终止后替换，不能阻塞最新输入，也不能回写。

局部折叠只更新受影响分组内部的布局，其他分组及其子节点沿用原位置；不把 ELK 整图重排后整体平移当作稳定布局。增长确实占用相邻分组空间时，仅做必要的局部避让；收起不把邻组拉回，不改变镜头。跨组边按最终节点位置修线。

自动排版由 ELK 完成；手动拖动按帧局部修复受影响路径，不把新端点拼到旧折点上。整体移动分组时内部路径与标签同步平移，跨组边单独修复；松手保存位置，不重新排版节点，也不逐帧持久化。

注释增删改及追问标记属于元数据刷新，复用未变化的视图，不改变分组尺寸、节点位置、连线路径或镜头，也不触发 ELK。默认分组尺寸仅用于新建，不能覆盖已测量和已布局的几何。连线只显示必要短条件，说明写入 summary 按需查看，不用关系类型补成常驻标签。

画布与编辑器 inline 的上／下一步共用同一导航状态。可导航关系为 control_flow、call、data_flow；不同后继构成分支并显示橙色分支图标。起点淡蓝，终点按成功/失败/中性显示。分叉时镜头框住候选，只突出候选节点与关系，候选橙色、预览紫色，原当前节点及路线恢复普通语义状态。不显示候选列表，鼠标悬停预览、点击确认；方向键循环、Enter确认、Escape退出，预览不改变已确认路径。原生请求固定到来源宿主与记录版本，不误操作后来激活的另一张答案。

### 4. Source is truth，任何抽象最后都必须落回源码

用户并不希望有一个“AI 生成的项目世界”替代真实代码。

图、inline、Trace、目录说明的目的都是：

> 更快找到并理解真实源码。

所以：

- 不隐藏源码。
- 不用生成页面替代源码。
- 不整体 dim 无关代码。
- 不把理解结果做成长篇文章。
- 涉及项目实现的节点可定位真实源码；教学节点可定位明确标注的独立样例。
- 图和源码默认一起看。
- 小屏笔记本尤其不能频繁在“整页图”和源码之间来回跳。

图可以主动放大到 Editor 区域，但这属于用户需要大图时的选择，不应该成为默认阅读方式。

---

### 5. Editor 必须非常安静

用户已经多次明确反感“为了表示理解状态而把编辑器弄得花里胡哨”。

当前原则是：

```text
普通源码
→ 完全正常

有 inline 信息
→ 显示很短的 inline

鼠标 hover 到有解释的行
→ 类似 JetBrains Insights 的柔和块状高亮

Trace 当前 step
→ 只突出当前真正需要注意的位置

之前已经看过 / 运行过的代码
→ Editor 不留下 visited-state 痕迹
```

历史执行路径属于 Graph，不属于 Editor。

编辑器 hover 直接复用旧版实现：只有进入短 inline 才触发高亮；inline 与对应代码块之间保持窄的连续命中区，块内移动不取消，移出或按下任意鼠标键清除。源码选区提问使用原生编辑器弹层，冻结当时的来源和选区；不自动切换到插件页面。同一源码标签内切换节点时平滑滚动到目标，新导航替换旧滚动，手动操作可中断。

原生选区冻结 UTF-16 半开起止偏移、全文版本和原文，保存时精确校验，允许同一行重复词。失配保留草稿，不退回全文搜索猜位置；跳转优先使用有效精确范围，旧记录保留安全定位，歧义明确报错。

节点的源码锚点用于导航和提示，不限制可提问的代码范围。在该节点已绑定的源码编辑器里，范围外的非空选区也沿用节点上下文；选区自身仍记录真实文件、原文、版本及偏移，不能扩大或替换成节点片段。没有该绑定的其他文档编辑器不继承节点，冻结后也不随后来选中的节点改写归属。

inline 紧贴锚定代码首行最近的上方，不被 Code Vision 或其他 block inlay 挤远。只保留一个圆形标识与短文本，圆形用几何绘制，去掉展示标签前重复的装饰圈号；上一／下一步箭头仍保留并可操作。源码移动、折叠和 inlay 动态变化后重新校验位置。

尤其不要：

- 每走一步就留一条绿色竖线。
- 高亮所有曾经执行过的行。
- 自动 dim 其他代码。
- 跳转后自动铺一大片背景。

核心原则是：

> 增强当前注意点，不留下操作历史噪音。

### 6. Understanding Graph 是关系表达，不需要人为划分很多“图类型”

曾经讨论过逻辑图、执行图、架构图等分类，后来认为产品层没必要这么分。

对用户来说就是：

> 几个节点、几条线、必要的信息。

节点可以代表：

- 逻辑块
- 代码位置
- 状态
- 事件
- 模块或子系统

边可以表达：

- 调用
- 条件
- 数据传递
- 包含
- 执行顺序
- 依赖

区别体现在数据和状态，不需要让用户理解“现在看的是哪一种专业图”。

---

### 7. Graph 和 Trace 要分清静态结构与真实执行

静态图可以表达：

```text
可能走 A
也可能走 B
```

真实 Trace 只能表达：

```text
这一次实际走了 A
```

没有运行时，用户可以自由探索不同可能分支。

运行后：

- 实际路径流动高亮。
- 没走的分支继续存在。
- 不把“没走”误解成“不可能走”。

对于循环、重试、递归，同一个图节点可能被命中很多次。

因此 Runtime 不能设计成：

```text
node → 一个最终值
```

而应该是：

```text
#1 node A
#2 node B
#3 node A
#4 node B
...
```

即：

> Runtime 是事件序列，不是节点属性。

---

### 8. Debugger 的价值是提供事实，不是让 AI 模拟执行

早期讨论过 synthetic trace、AI 模拟变量等方向，后来逐渐收缩。

诊断真实程序行为时，证据优先级明确：

```text
真实执行 > mock 边界 > AI 猜运行结果
```

IDE / Debugger 提供：

- 实际走过哪里。
- 调用栈。
- 真实变量。
- 异常。
- 分支。
- 运行顺序。

Agent 做的是：

- 哪些位置值得观察。
- 哪些事件对用户当前问题有意义。
- 如何压缩成几个 meaningful steps。

不是让 AI 一次判断“应该按几次 F8”。

---

教学允许静态推演与模拟数据，明确标为演示，不要求每节都获取 trace。可以先用小例子理解机制，再回到项目看对应关系；具体调度、变量和异常需要实际运行证据。教学代码随页面保存，默认在原生只读编辑器显示；用户要修改或运行时再创建 Scratch 或练习文件。统一画布和 Cluster 不变，通过普通组件组合、选择和显隐组织实验，不改成聊天或滚动文章页，也不增加通用详情层。

多行代码和 JSON 在画布上使用紧凑入口，点击打开 IDEA 原生只读编辑器；少量数值和状态留在页面中。源码快照、教学代码和页面数据分别标识，源码快照另有定位当前文件的入口。组件快照冻结打开时的值、状态及 UTF-16 选区，控件变化不改写已打开内容。JSON 文本的解析视图与原始字符串分开，保留原文，不能直接去掉转义字符。Card、Badge 用信息、成功、警告、危险等语义色作轻强调，正文仍使用正常前景色。

生成式 UI 服务于源码理解。先确定用户的具体困惑、需要建立的职责与关系或状态认识，再选择最小表达；源码节点和连线足够时直接使用。生成式 UI 可以提供合适的空间组织，也可以通过操作揭示条件与结果的联系，不要求每次发明交互。需要比较的对象保持同时可见，Tabs 和折叠按阅读任务选择；源码声明直接定位到原生编辑器，快照仅用于确有价值的对照。模拟数据、时间和执行与实际运行明确区分。少数复杂问题上明显减少理解负担，就足以保留这项按需能力；是否值得保留整个 JCEF 分支仍需单独评估，暂不验证原版。用户继续使用 IDEA 编辑器标签，不增加卡片内原生覆盖层或额外代码面板。

### 9. Trace 的显示位置和实际观测位置不是一回事

这是后面必须一直记住的实现细节。

例如用户想理解：

```kotlin
val child = branchFrom(...)
```

想显示：

```text
child.id = conv-b
```

Debugger 真正能读取 `child` 的地方，可能已经到了下一条可执行指令。

所以：

```text
display node
≠
observation location
```

Runtime event 应该通过稳定 `nodeId` 关联 Understanding Graph，而不是通过行号关联。

---

### 10. 行号不是可靠锚点，Re-entry 是核心能力

这个产品不是只解决：

> “我今天终于看懂了。”

还要解决：

> “我后天忘了，怎么一分钟重新进去？”

所以源码锚点不能只是：

```text
Foo.kt:123
```

代码一改就会漂。

应该综合：

```text
文件
symbol / class / function
signature
anchor text
版本
行号 hint
必要时上下文指纹
```

由 PSI 重新定位。

而且：

> 找回了位置，不代表原来的理解仍然正确。

位置新鲜度和语义新鲜度需要分开判断。

---

### 11. 历史问题需要保存，但不是保存完整 Chat History

用户需要的是：

```text
我之前研究过什么？
我当时看到哪张图？
我停在哪一步？
我从哪段源码问出来的？
```

不是把 Codex / Claude 的整段聊天复制一份。

问题树表达的是**理解关系**，不是时间顺序。

例如：

```text
A Session 分支怎么工作？
├─ B 为什么恢复 draft？
│  └─ D RestoredDraft 是什么？
├─ C 为什么先 save？
└─ E invalid branch 怎么处理？
```

实际聊天顺序完全可能是：

```text
A → B → C → D → E
```

但不能按聊天顺序机械缩进。

---

### 12. 问题的“来源”和“归属”必须分开

用户可能正在研究 B 时突然想到一个实际上属于 A 的问题。

所以至少区分：

```text
origin
→ 我从哪里产生这个问题？

parent
→ 这个问题在理解结构里属于谁？
```

可能出现：

```text
originFrame = B
parentFrame = A
```

这是正常情况。

contextToken 用来冻结“用户提出问题那一刻”的上下文，避免 Agent 分析过程中用户已经移动到其他地方，回来后结果挂错位置。

---

### 13. Agent 不应该成为插件内部的一套 AI 系统

用户明确不想再配置一套 AI。

不做：

- OpenAI Provider。
- Anthropic Provider。
- OpenRouter。
- API Key。
- 模型选择。
- ACP Client。
- 自己的完整 Chat UI。

用户继续使用已经配置好的：

```text
Codex
Claude
Junie
其他 Coding Agent
```

插件通过 IDEA MCP 暴露自己的呈现能力。

Agent 的“宿主”也不是产品前提。它今天可能是 AI Chat，也可能是 Air、CLI、独立 Agent UI 或其他支持 MCP／ACP 的环境。近期 JetBrains Air 的方向进一步说明 agentic 工作会跨 surface、跨服务发展，因此不能把 AI Chat 的生命周期、会话模型或内部 API 写进本插件的核心协议。

插件只需要稳定处理三件事：准备问题上下文、让某个宿主把任务交给 Agent、接收 Agent 经 MCP 返回的结构化结果。首轮允许用“复制问题 + contextToken”完成 handoff；以后若宿主提供正式 task handoff，只替换交接适配层。

核心边界可以概括成：

> Agent 负责分析、生成和更新理解；插件负责验证引用、保存状态、呈现和回放。Agent 可以运行在不同宿主中，插件不拥有也不假设那个宿主。

---

### 14. Walkthrough 是重要参考，也是明确的反例来源

Walkthrough 有几个值得借鉴的地方：

- Agent 生成理解结果。
- 结果和源码位置绑定。
- 支持逐步浏览。
- 可以围绕局部代码继续理解。

但它的局限也直接影响了本项目方向。

第一，它的主要载体仍然偏**AI 文本 / explanation steps**。即使锚到了代码，长时间使用仍然很容易变成“Markdown walkthrough”，没有解决用户最讨厌的阅读负担。

第二，根据目前看到的实现，它为了允许用户在 Walkthrough UI 中继续问问题，需要类似：

```text
await_walkthrough_question
```

这样的等待机制。

Agent 要持续等待插件里的问题，涉及：

- 长轮询
- 超时
- 排队
- processing
- Agent 没在监听
- 状态防闪烁

这些复杂性本质上来自：

> Plugin 想主动向 Agent 发起下一轮任务。

当前 Lessplain 希望尽量避免复制这套架构。

因此当前可靠链路仍然是：

```text
Plugin 捕获 question + contextToken
→ 复制到用户当前的 Agent 宿主，或由稳定的 handoff adapter 交接
→ Agent 调 MCP 返回结果
→ Plugin 展示
```

关键不是一定“回到 AI Chat”，而是 handoff 不应要求 Agent 长时间驻留等待插件。插件里的“就地提问”可以作为理想 UX，但在宿主没有稳定 task handoff 时，只提供复制载荷；以后即使 JetBrains 从 AI Chat 转向 Air 或新的 agentic surface，核心协议也不需要重做。

第三，Walkthrough 也暴露了源码锚点容易漂移的问题。这进一步强化了本项目把 Re-entry、PSI anchor 和 stale 判断作为一等能力，而不是附加功能。

---

### 15. Project Tree 和 Project Graph 解决的是全局认识

用户习惯接触新项目时先：

```text
看根目录
→ 看主要文件夹
→ 一层层展开源码目录
→ 大概知道各自负责什么
→ 再挑一个地方深入
```

所以 Project Tree 是最自然的全局入口。

目录说明应该极短：

```text
session       会话树 / 分支
persistence   SQLite / snapshot
agent         ReAct / Hooks
```

而不是每个目录一段总结。

Project Graph 也必须保留，因为文件系统不等于逻辑架构。

它解决：

```text
这些散落在不同目录里的东西，其实共同组成什么？
```

不能只有“一文件一节点”的平铺图。全局图应覆盖整个项目，允许查看文件和函数，也支持跨目录的职责聚合：

```text
Session
→ 1 个目录 + 12 个文件 + 若干 class
```

IDE 提供结构事实，Agent 做语义聚合。

证据不足宁愿：

```text
Unclear / Cross-cutting
```

也不要编一个漂亮架构。

---

### 16. Diff 已经成为新的正式产品方向

后续不仅要理解“现在代码怎么工作”，还应该能理解：

> 这次改动改变了什么？

但仍然遵守同样原则。

不是：

```text
Diff → AI 长篇总结
```

而是按变化类型选择表达：

- 普通文本变化直接看原生 diff。
- 调用顺序 / 条件变化可以画局部关系图。
- 跨文件职责变化可以展示相关区域。
- 影响必须有依赖或 runtime 证据。
- 修改动机没有 commit / discussion / 作者说明时，可以明确“不知道”。

不要把相关性写成因果。

---

### 17. UI → Source 暂时不是 MVP 核心

精确跨框架实现：

```text
点屏幕上的一个按钮
→ 精确跳到任意框架源码
```

没有简单统一方案。

所以暂时不能让它阻塞主产品。

可以保留弱能力：

```text
UI Outline
→ 给出大概区域
→ 给候选源码
```

但必须明确只是区域级提示。

---

### 18. “改这个会怎么样”交给真实框架

不自建：

- Compose Preview。
- React renderer。
- Vue renderer。
- 跨框架模拟 UI。

用户修改真实代码后，用项目自己的：

```text
Compose Hot Reload
React HMR
Vue HMR
...
```

查看效果。

插件只帮助回答：

```text
这个参数控制什么？
它在哪里？
它跟哪些逻辑有关？
```

---

### 19. 原型只是交互验证，不代表真实架构

React / HTML Prototype 可以大量使用假数据。

但必须防止假数据反过来污染设计。

尤其不能因为原型方便就引入：

- Agent 能被按钮直接调用。
- 手写 node x/y。
- 真实产品不存在的执行按钮。
- 行号作为正式 source identity。
- 一个节点只有一个 runtime value。

真实产品里：

```text
Graph layout
→ 插件自动算

Agent work
→ Agent 发起

Runtime
→ 有序 TraceHit

Source identity
→ PSI anchor

Prototype controls
→ 只用于演示
```

---

## 最后可以压成 8 条不可轻易违反的原则

```text
1. Source is truth。
2. 按问题选择图、短文字或交互，压缩重复与无关信息。
3. 用户问题驱动，不替用户猜“应该学什么”。
4. Project Tree 建立物理坐标，Project Graph 建立语义全局图。
5. IDE / Debugger 提供事实，Agent 负责筛选和组织。
6. Runtime 是事件序列，不是节点最终状态。
7. 理解结果必须能重新进入，并能判断旧结果是否 stale。
8. Agent 负责产生理解，Plugin 负责验证、保存、呈现和回放；不要把 AI Chat 或任何单一 Agent 宿主写进核心协议。
```
